Findings:

1. High: the debounce state machine never confirms a new scene while sensor updates keep arriving, so `currentScene` can stay `null` indefinitely and playback falls back to `RESTING`.
[SceneStateMachine.kt](/Users/k1810895/Code/cadence/app/src/main/java/io/cadence/music/domain/SceneStateMachine.kt#L36) cancels and restarts the 15s timer on every `process()` call whenever the candidate differs from `lastEmittedScene`. Because `SensorStateCollector` emits continuously, a stable new candidate like `RUNNING` keeps resetting the timer every few seconds instead of being confirmed after 15 seconds. That flows into [MusicOrchestrator.kt](/Users/k1810895/Code/cadence/app/src/main/java/io/cadence/music/audio/MusicOrchestrator.kt#L99), which then primes playback with `Scene.RESTING`.

2. High: scene changes can mix old and new audio because buffer regeneration does not cancel in-flight generation jobs or fully reset the singleton queue.
[AudioBufferManager.kt](/Users/k1810895/Code/cadence/app/src/main/java/io/cadence/music/audio/AudioBufferManager.kt#L56) only drains items already present in the channel, then immediately reprimes. Any older `enqueueNext()` coroutine started before the scene change is still running from [AudioBufferManager.kt](/Users/k1810895/Code/cadence/app/src/main/java/io/cadence/music/audio/AudioBufferManager.kt#L68) and will still `send()` its stale file into the same channel after the reprime. That means the player can consume audio for the previous scene after a confirmed transition, and suspended sends can also clog the two-item queue.

3. Medium: `startDetection()` leaks a `confirmedScene` collector every time the player screen is recreated, causing duplicate scene-handling work after navigation/re-entry.
[MusicOrchestrator.kt](/Users/k1810895/Code/cadence/app/src/main/java/io/cadence/music/audio/MusicOrchestrator.kt#L78) launches a collector for `confirmedScene` but never stores or cancels that job in `stop()`. `stop()` only cancels `detectionJob` at [MusicOrchestrator.kt](/Users/k1810895/Code/cadence/app/src/main/java/io/cadence/music/audio/MusicOrchestrator.kt#L122), while [PlayerViewModel.kt](/Users/k1810895/Code/cadence/app/src/main/java/io/cadence/music/ui/player/PlayerViewModel.kt#L54) calls `orchestrator.stop()` when the screen is cleared. Reopening the player therefore stacks collectors, so one confirmation can trigger multiple `drainAndReprime()` calls.

4. Medium: the permissions screen can strand users even when location permission is already sufficient.
[PermissionsScreen.kt](/Users/k1810895/Code/cadence/app/src/main/java/io/cadence/music/ui/permissions/PermissionsScreen.kt#L52) initializes `locationGranted` to `false` and never checks the current permission state on entry, so after an app relaunch the Continue button may remain disabled until the user requests permission again. Separately, the launcher callback at [PermissionsScreen.kt](/Users/k1810895/Code/cadence/app/src/main/java/io/cadence/music/ui/permissions/PermissionsScreen.kt#L65) only treats `ACCESS_FINE_LOCATION` as success, but [LocationService.kt](/Users/k1810895/Code/cadence/app/src/main/java/io/cadence/music/data/sensor/LocationService.kt#L101) accepts either fine or coarse permission. A coarse-only grant is therefore blocked by the UI even though the service would run.
